## 📖 Overview

A design system built in three layers, so a decision lives in **one** of them rather than in all of them. Color is settled in the tokens, behavior in the base, appearance in the components.

---

## 🧱 Three Layers, Four Packages

| Layer          | Package            | What is in it                                                                                                                                   |
| -------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Values**     | `style-tokens`     | Color, spacing, radius, type, shadow, motion. One source, four outputs: CSS variables, TypeScript objects, utility classes, a Tailwind v4 theme |
| **Behavior**   | `base-react`       | 18 headless components: 17 wrapping a Radix package each, and `Button`, which is ours. Keyboard, focus and ARIA, and no styling at all          |
|                | `behavior-react`   | Interaction Radix does not cover. `usePress`, so a link or a `div` styled as a button still answers the keyboard                                |
| **Appearance** | `components-react` | 23 components plus `Theme`. The only layer that decides what anything looks like                                                                |

- **Every decision here is one of three kinds: what a value is, how a thing behaves, how it looks.** One layer answers each, so changing a color does not mean opening the file that traps focus.
- Four packages because `base-react` is built on Radix, and the behavior Radix does not cover is kept separately in `behavior-react`.

## 🔧 Technical Challenges & Solutions

### 1. One bundle → per-component entries

**🔍 Problem**: The package shipped as one barrel bundle behind two entry points, one for the JavaScript and one for the CSS, so a single `'use client'` inside it made all 24 components client-only and no consumer on Next.js App Router could render any of them from a server component.

**💡 Solution**

- Per-component entries behind a subpath `exports` map. esbuild has no `preserveModules`, so the entries are generated by scanning the source tree, and the barrel is excluded because building it brings the single bundle back.
- Splitting rather than tree-shaking, because neither of the two costs is shakeable: `'use client'` is decided per file _before_ the bundler runs, and CSS has no way to say who uses `.dialog { … }`.

```javascript
// packages/esbuild-config/index.js
const scanComponentEntryPoints = (srcDir = 'src') => {
  const entryPoints = [];
  const scanDirectory = (dir, basePath = '') => {
    fs.readdirSync(dir).forEach(item => {
      const itemPath = path.join(dir, item);
      if (!fs.statSync(itemPath).isDirectory()) return;
      // A folder with an index is a component. Do not descend further.
      if (fs.existsSync(path.join(itemPath, 'index.tsx'))) {
        entryPoints.push(`${srcDir}/${basePath}${item}/index.tsx`);
      } else {
        scanDirectory(itemPath, path.join(basePath, item));
      }
    });
  };
  scanDirectory(srcDir);
  return entryPoints.filter(e => !e.includes('src/index.ts'));
};
```

**✅ Outcome**

- Importing nothing but `Button`, gzipped: **11,217 → 1,485 B** transferred and **74,210 → 3,740 B** after decompression. **7.6× on the wire, 20× on what the browser parses.**
- A perfect tree-shake would still have left 5,026 B, and **4,322 B of that is CSS**, which is the measurement that made splitting the only route.

### 2. Compound components could not cross the RSC boundary

**🔍 Problem**: The twelve compound components broke the build when rendered from a server component, with `Dialog.Root` arriving as `undefined`.

**💡 Solution**

- A `'use client'` module's exports cross the boundary as _references to client components_ rather than as values, so `Dialog` arrives as one reference with no properties on it to read.
- Every part is exported by name as well. This is what Radix does, and it breaks nothing that already worked.

```typescript
export const Button = forwardRef(...)          // function → one reference ✅
export const Dialog = { Root, Trigger, ... }   // object   → one reference ❌

export const Dialog = { Root, Trigger, Content, Title }; // unchanged
export const DialogRoot = Root; // a shape a reference can carry
export const DialogTrigger = Trigger;
```

**✅ Outcome**

- Verified both directions: a server page rendering all twelve prerenders and returns their content in the HTML, and `Dialog.Root` still works everywhere it did before.
- `splitting: true` in the same pass hoisted the shared code each entry had been copying: **33,585 → 24,936 B raw**.

### 3. Color is measured, not chosen

**🔍 Problem**: A palette picked by eye cannot answer "is this legible", and a contrast check run once during design does not survive the palette being retuned.

**💡 Solution**

- 14 chromatic scales and 3 neutrals, 13 steps each, generated rather than picked.
- The build measures white and black against every solid fill, keeps whichever clears 4.5:1, and writes the ratio out as data rather than as a claim.

```typescript
// Generated. packages/style-tokens/src/variables/color/static/contrast.ts
red:  { step: 500, fill: '#eb1414', white: 4.52, black: 4.64, chosen: 'white' },
blue: { step: 500, fill: '#0868f7', white: 4.85, black: 4.33, chosen: 'white' },
cyan: { step: 500, fill: '#07ace4', white: 2.62, black: 8.03, chosen: 'black' },
```

**✅ Outcome**

- The documentation reads that file, so it renders the measurements: where both colors clear it says which convention picked, and where one misses it says by how much.
- For reference, Radix Colors guarantees contrast for steps 11 and 12 only, and in APCA. Step 10, the hovered solid, says nothing about contrast at all.

### 4. Retheming without rebuilding

**🔍 Problem**: Changing an accent or a corner radius usually means either a rebuild or a prop threaded through every component that could be affected.

**💡 Solution**

- `Theme` writes two attributes on a wrapper, and every component reads its values through CSS variables rather than through props.
- The Tailwind utilities compile to `var()` rather than to copied values, so one class stays correct in both themes.

```tsx
<Theme accentColor="purple" radius="large">
  <App />
</Theme>
```

**✅ Outcome**

- **23 components change appearance, none is rebuilt, and none takes a new prop.**
- No `dark:` variant anywhere in the system, because the variable a utility points at is the thing that changes.

## 🚀 Getting Started

```bash
pnpm add @minuk-hwang-design-system/components-react
```

```tsx
// Once, at the root of the app.
import '@minuk-hwang-design-system/style-tokens/style-tokens.css';

// Per component, so you take only the CSS you use.
import { Button } from '@minuk-hwang-design-system/components-react/button';
import '@minuk-hwang-design-system/components-react/button/style';

export default function App() {
  return <Button>Publish</Button>;
}
```

### Local development

```bash
pnpm install
pnpm build:packages      # the four packages, in dependency order
pnpm dev:docs            # the documentation site
```
